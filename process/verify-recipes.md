# Verify-рецепты для BSL style-pass

## Назначение

Этот файл задает verify-слой после edit-pass.

Он различает два типа проверок:

- **machine checks** — кодировка, переводы строк, diff-scope, grep-паттерны;
- **judgement checks** — визуальная и семантическая проверка diff-а на опасные
  маркеры поведения и внешнего контракта.

Verify-проход выполняется после auto-fix и перед `process/hard-gates.md`.

## Общие правила

- Проверяйте каждый измененный файл отдельно.
- Не заявляйте, что machine-check выполнен, если инструмент недоступен.
- Если среды не хватает, используйте честный fallback и явно фиксируйте его в
  выводе.
- После verify обновите статусы соответствующих checks в coverage-table.

## Многофайловый цикл

Если изменено несколько файлов, повторяйте verify по каждому пути.

Пример безопасного цикла:

```bash
for path in <paths>; do
  file -b "$path"
  git diff -- "$path"
done
```

Что проверять:

- кодировка и переводы строк не изменились неожиданно;
- diff не содержит чужих или случайных правок;
- scope diff-а соответствует intended fix-pass.

## Fallback, если окружение неполное

### Если нет `git`

Используйте одно из решений:

- сохраненную копию файла «до» и `diff -u`;
- diff в редакторе;
- снапшот фрагмента до/после, если scope очень локален.

Если ничего из этого нет, не утверждайте, что diff был машинно проверен.
Опишите, что именно удалось проверить вручную.

### Если нет `file`

Проверьте кодировку и переводы строк доступным инструментом среды или editor-а.
Если это не удалось, честно укажите ограничение.

### Если нет `rg`

Используйте `grep -nE` или editor search. Результат по смыслу должен быть тем
же, а не «примерно похожим».

## Всегда после реальной BSL-правки

Минимальный набор:

```bash
file -b <path>
git diff -- <path>
```

Проверьте, что:

- файл остался в ожидаемой кодировке;
- переводы строк не поплыли;
- diff содержит только intended изменения;
- не появились случайные whitespace-изменения вне planned scope.

## Tab-rhythm пустых строк BSL

Если scope включает BSL-файл целиком или whitespace-правку внутри метода,
обязательно запустите машинный guard пустых строк:

```bash
python3 -B scripts/check_bsl_blank_line_tab_rhythm.py <path>
```

Если guard нашёл нарушения и scope допускает запись, примените точечный fix-pass
и сразу повторите проверку:

```bash
python3 -B scripts/check_bsl_blank_line_tab_rhythm.py --fix <path>
python3 -B scripts/check_bsl_blank_line_tab_rhythm.py <path>
```

Эта проверка не заменяет judgement-pass по `references/bsl-formatting.md`, но
закрывает минимальный машинный инвариант: пустая строка внутри
`Процедура` / `Функция` не должна оставаться без tab-уровня текущего BSL-блока.

## Текст запроса

Если в scope был `Запрос.Текст` или query-helper, дополнительно проверьте:

```bash
rg -n "\| +" <path>
rg -n 'Запрос\.Текст = ТекстЗапроса|Функция ТекстЗапроса|ВозвращаемоеЗначение = "' <path>
```

Проверьте:

- после `|` нет структурных пробелов вместо табов;
- query-helper начинается на строке `ВозвращаемоеЗначение = "`;
- основной метод задает `Запрос.Текст` через helper, если профиль применим.

## Поведенческий предохранитель: опасные маркеры

Перед финалом визуально просмотрите diff рядом с маркерами риска:

```bash
git diff -- <path>
```

Ищите изменения рядом с:

- `Если ЗначениеЗаполнено`;
- `СоздатьДокумент`;
- `ТекущаяДата`;
- `ВызватьИсключение`;
- `Получить...ПоУмолчанию`;
- `ПолучитьЗначениеПоИдБУСОбъекта`;
- `ПолучитьЗначениеПоXML`;
- ранними `Возврат` и условиями fallback-веток.

Отдельно проверьте присваивания через разыменование:

```bash
git diff -- <path> | rg "ЗначениеЗаполнено|\.[А-Яа-яA-Za-z0-9_]+ = .+\.[А-Яа-яA-Za-z0-9_]+"
```

Если такой маркер изменился, нужен один из двух исходов:

- либо зафиксирована явная причина и изменение признано намеренным;
- либо поведенческая защита возвращена, а style-pass ослаблен.

## Coverage и rerun

В конце verify-прохода проверьте coverage-table:

- каждый `FIXED`-check действительно перепроверен;
- все mandatory+applicable checks имеют terminal status;
- `UNRUN` не осталось;
- `N/A` снабжены причинами;
- checks `SAF-*`, `VRF-*`, `HGT-*` обновлены после последнего edit-pass.

## Что обязательно вынести наружу

Если verify был частично ограничен средой, в финальном ответе нужно честно
написать:

- какой machine-check не удалось выполнить;
- какой fallback использовался;
- что осталось только на judgement-проверке.
