# Стиль 1С BSL-кода

Навык поднимается по имени `1c-bsl-code-style` (хостом ZCode) либо
подключается контуром 1c-zcode.

## Назначение

Навык задает практический стиль 1С/BSL-кода при написании, рефакторинге и
style-review. Его задача — выбрать удачную локальную форму кода: шапку модуля,
дробление методов, промежуточные переменные, doc-comments, форматирование.

Это не формальное review по `v8std` и не замена навыка
`$1c-bsl-review-standards`.

## Когда использовать

- написание нового кода 1С/BSL;
- упрощение или перепроектирование существующего модуля;
- читаемость, структура, именование без полного standards-review;
- борьба с оверинжинирингом;
- doc-comments;
- BSL-форматирование при точечной правке;
- style-review реального BSL-кода с автоисправлением локальных
  детерминированных проблем.

Style-only запросы (регистр `Не`/`И`/`Или`, форматирование, локальное
именование, doc-comments, декомпозиция) без явного запроса на `v8std`
остаются в этом навыке. Если пользователь просит именно review по стандартам,
запускайте `$1c-bsl-review-standards`.

## Режимы

- `consultation` — вопрос о форме кода без реального scope. Читайте только те
  правила, которые относятся к вопросу; базовое ядро —
  `references/principles.md` и `references/anti-overengineering.md`.
- `real-code` — написание, правка или review реального кода. Выполняется
  процедура ниже полностью; companion-применение внутри внешнего pipeline
  (standards/BSP) — тот же полный режим, без облегчённой версии.
- `skill-audit` — аудит самого навыка: согласованность `SKILL.md`, rule-паков,
  профилей, guard-скрипта и тестов.

## Процедура `real-code`

1. Inventory: что в scope — целый `*.bsl`-модуль, whitespace-правки,
   `Запрос.Текст`, orchestration-модуль, граница legacy/внешнего контракта,
   затронутые методы, есть ли право на запись.
2. Прочитать правила, применимые к scope. Для целого модуля сначала
   `references/module-header.md` (верхний уровень файла до анализа методов);
   для whitespace-правок обязателен `references/bsl-formatting.md`; для
   любых правок — `references/behavior-change-guard.md`.
3. Прогнать машинный guard по изменяемым `*.bsl`:
   `python3 scripts/bsl_style_check.py <path>` (при праве на запись — с
   `--fix`).
4. Проверить семантику, которую guard не покрывает: naming, декомпозиция,
   промежуточные переменные, overengineering, уместность doc-comments,
   профили при подтверждённой применимости.
5. Локальные детерминированные findings исправлять самостоятельно, если scope
   допускает запись. Спрашивать пользователя только о спорных, неоднозначных
   или тяжёлых по последствиям решениях.
6. После правок повторно прогнать guard и проверить diff: только intended
   изменения; условия `Если`, fallback-ветки, момент создания объектов,
   источник даты и вызываемый API не затронуты
   (`references/behavior-change-guard.md`).
7. В финальный ответ вынести: что исправлено автоматически, что осталось
   residual findings или рисками, и ограничения проверки, если они были.

Не завершайте работу сырым списком исправимых findings, если их можно
безопасно закрыть самостоятельно.

## Правила

Каждое правило имеет один канонический дом; примеры «менее удачно → лучше»
живут в том же файле.

- `references/principles.md` — ядро style-эвристик.
- `references/anti-overengineering.md` — как не перегрузить код абстракциями.
- `references/bsl-formatting.md` — табы, пустые строки, регистр `Не`, `И`,
  `Или`.
- `references/module-header.md` — шапка модуля и верхний уровень файла.
- `references/naming.md` — именование.
- `references/method-composition.md` — декомпозиция, промежуточные значения,
  конструкторы, форма функций, ветвление.
- `references/call-layout.md` — компактная и многострочная форма вызовов.
- `references/behavior-change-guard.md` — стилевая правка не меняет поведение.
- `references/doc-comments.md` — doc-blocks и их уместность.
- `references/review-feedback.md` — legacy/внешние границы, явные
  преобразования, глобальное состояние.

## Профили

Подключаются только при подтверждённой применимости, это не универсальные
нормы любого модуля:

- `profiles/query-texts.md` — `Запрос.Текст` через helper-ы и область
  `ТекстыЗапросов`.
- `profiles/orchestration.md` — orchestration-модули и их сценарный ритм.

## Машинный guard

`scripts/bsl_style_check.py` закрывает детерминированные правила:

- `tab-rhythm` — пустые строки внутри методов держат tab-уровень блока (fix);
- `operator-case` — операторы только `Не`, `И`, `Или` (fix);
- `empty-ctor-parens` — пустой конструктор со скобками (fix);
- `comma-space` — пробел после запятой в списке аргументов (fix);
- `struct-ctor-args` — `Новый Структура` не более чем с одним значением;
- `if-nesting` — вложенность `Если...Тогда` не глубже двух уровней;
- `return-expression` — прямой `Возврат Выражение;` вместо
  `ВозвращаемоеЗначение`.

Прогоняйте guard при любой BSL-правке и после auto-fix повторно. Guard не
закрывает семантические проверки (naming, декомпозиция, doc-comments,
поведение) — они остаются на агенте.

## Жёсткие правила

MUST:

- для целого `*.bsl`-модуля сначала проверять шапку и верхний уровень файла,
  потом методы;
- при любой BSL-правке прогонять `scripts/bsl_style_check.py`, после fix —
  повторно;
- исправлять локальные детерминированные findings при наличии права на запись;
- каждый edit-pass сверять с `references/behavior-change-guard.md`;
- профили применять только при подтверждённой применимости.

MUST NOT:

- не менять поведение под видом стиля: защитные условия, порядок
  fallback-веток, момент создания объекта, источник даты, вызываемый API;
- не удалять табы на пустых строках внутри методов как trailing whitespace;
- не запускать массовое переформатирование модуля, если задача не была именно
  форматированием;
- не создавать вложенность `Если...Тогда` глубже двух уровней;
- не восстанавливать doc-comments ради шаблона;
- не подменять style-review формальным standards-review;
- не принимать унаследованную локальную форму за норму, если она расходится с
  правилами навыка и не требуется внешним контрактом.

## Граница с другими навыками

- `$1c-bsl-review-standards` — формальные требования `v8std`, включая
  `#std647` по именованию. При конфликте по локальной форме кода
  (форматирование, декомпозиция, doc-comments) приоритет у текущего навыка.
- `$1c-bsl-architecture-ddd` — архитектурная декомпозиция и границы
  ответственности.
- `$1c-bsl-bsp-patterns` — выбор штатных методов БСП.

Текущий навык отвечает именно за локальную форму кода и прикладные
style-эвристики.
