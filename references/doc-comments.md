# Заголовки функций и процедур

## Назначение заголовка

Заголовок метода нужен не для формального заполнения шаблона, а для быстрой
ориентации в контракте метода.

Хороший заголовок отвечает на один из двух вопросов:

- что здесь действительно важно понять до чтения тела метода;
- почему здесь отдельная аннотация не нужна.

Если заголовок не добавляет нового смысла, не надо имитировать полезность
повтором имени метода.

## Базовое правило

Если суть метода уже очевидна из его имени, первой строкой заголовка
предпочтительно писать:

`// Аннотация не требуется.`

После этого нужно нормально описать параметры и возвращаемое значение, если они
есть.

Такой вариант лучше, чем:

- дублировать имя метода в описании;
- оставлять устаревший текст от соседнего метода;
- держать временную заглушку `//TODO: <Описание функции>`.

## Проектное уточнение

В этом проекте документирующий комментарий оставляется у каждого затронутого
метода, включая неэкспортные методы.

Если имя метода самодостаточно и отдельная первая строка не добавляет новой
информации, используйте форму:

```bsl
// Аннотация не требуется.
//
```

После нее при наличии параметров добавляется секция `Параметры:`, а при наличии
возвращаемого значения — секция `Возвращаемое значение:`.

Для составных типов нужно раскрывать не только контейнер, но и схему данных:

- `Структура`, `ФиксированнаяСтруктура`
- `ТаблицаЗначений`, `ДеревоЗначений`
- `Массив`, `ФиксированныйМассив`, если элементы имеют собственную схему

Приоритетный способ описания схемы — ссылка на `ФункцияКонструктор`.
Если для параметра или возвращаемого значения уже существует подходящая
`ФункцияКонструктор`, используйте ссылку `см. <Модуль>.<ФункцияКонструктор>`.

Явное перечисление полей, колонок и вложенных типов допускается только:

- в комментарии самой `ФункцияКонструктор`;
- если подходящей `ФункцияКонструктор` еще нет и выделять ее в этом месте
  нецелесообразно.

Голый контейнер `Структура` или `ТаблицаЗначений` без схемы допустим только
для действительно универсальных методов, где фиксированная схема не является
частью контракта.

## Когда аннотация не требуется

Используйте `Аннотация не требуется.`, если имя метода уже достаточно точно
объясняет его роль:

- `ПодготовкаСклады`
- `ТекстЗапросаПодготовкаСклады`
- `ОрганизацииИзКПК`
- `ПакетыЭтапаСценарии`

Это особенно уместно для модулей, где много однотипных вспомогательных методов и читателю
важнее быстро проверить параметры и возвращаемое значение, чем читать
тавтологию над каждым методом.

## Когда нужна содержательная аннотация

Аннотация нужна, если без нее по имени метода неочевидны:

- контракт на границе внешнего обмена или формат выходных данных;
- важный побочный эффект;
- допущения и ограничения;
- необычная нормализация;
- отличие от похожего соседнего метода;
- причина, по которой метод вообще выделен отдельно.

Хорошая первая строка в таком случае объясняет именно это отличие, а не
пересказывает имя метода.

## Что нельзя оставлять в финальном коде

- `//TODO: <Описание функции>`
- `<Параметр1>`, `<Тип.Вид>`, `<описание параметра>`
- заголовок, который описывает другой метод
- описание возвращаемого значения, не совпадающее с реальным return-contract
- фразы вида `Подготавливает данные для соответствующего этапа выгрузки.`, если
  они не помогают отличить один метод от другого

## Правила для параметров и возвращаемого значения

1. Описывайте реальную семантическую роль параметра в текущем методе.
2. Если параметр является контейнером результата, пишите это явно.
3. Если функция возвращает представление для внешнего контракта, структуру данных обмена или нормализованное значение,
	   это надо назвать прямо.
4. Если функция может вернуть пустое значение по умолчанию, это полезно отметить
	   в блоке возвращаемого значения.
5. Если тип составной и схема стабильна, не дублируйте явное описание в
	   потребителе: ссылайтесь на `ФункцияКонструктор`.
6. Если текущий метод сам является `ФункцияКонструктор`, документируйте поля,
	   колонки и вложенные типы прямо в его блоке `Параметры:` или
	   `Возвращаемое значение:`.
7. Если важное пояснение относится к конкретному параметру или возвращаемому
	   значению, оно должно жить именно в блоке `Параметры:` или
	   `Возвращаемое значение:`, а не в отдельном комментарии после сигнатуры
	   метода или внутри тела.
8. Если имя параметра сохранено ради совместимости, а фактическая семантика уже
	   другая, это нужно явно раскрывать в строке описания параметра.
9. В русском документирующем комментарии не оставляйте нерасшифрованный
	   внутренний жаргон вроде `stub`, если его можно заменить точным русским
	   описанием совместимости или роли параметра.

## Антипаттерн: смысл параметра вынесен из блока `Параметры:`

Плохо:

```bsl
// Аннотация не требуется.
//
// Параметры:
//  ИдПартнера - Структура - структура с полем Ид.
//
Функция НайтиПартнера(ИдПартнера)
	// Примечание: имя параметра сохранено для совместимости со существующим stub,
	// но фактически передается структура с полем Ид.
```

Лучше:

```bsl
// Аннотация не требуется.
//
// Параметры:
//  ИдПартнера - Структура - имя параметра сохранено для совместимости с прежним
//               контрактом; фактически ожидается структура с полем Ид.
//
Функция НайтиПартнера(ИдПартнера)
```

## Предпочтительные шаблоны

### 1. Очевидный метод

```bsl
// Аннотация не требуется.
//
// Параметры:
//  ДанныеДляОтправки - см. ОбменСлужебный.ДанныеДляОтправки
//
Процедура ПодготовкаСклады(ДанныеДляОтправки)
```

### 2. Неочевидная нормализация

```bsl
// Нормализует наименование организации для внешнего контракта обмена.
//
// Параметры:
//  НаименованиеОрганизации - Строка - Исходное наименование организации.
//
// Возвращаемое значение:
//  Строка - Нормализованное наименование без служебных префиксов и хвостов.
//
Функция НормализованноеНаименованиеОрганизации(НаименованиеОрганизации)
```

### 3. Возврат готового query-text

```bsl
// Аннотация не требуется.
//
// Возвращаемое значение:
//  Строка - Текст запроса подготовки складов.
//
Функция ТекстЗапросаПодготовкаСклады()
```

### 4. Потребитель составного контракта

```bsl
// Аннотация не требуется.
//
// Параметры:
//  ПараметрыПодключения - см. ИнтеграцияСлужебный.ПараметрыПодключенияКAPI
//
// Возвращаемое значение:
//  ТаблицаЗначений - см. ИнтеграцияСлужебный.РезультатПроверкиПодключения
//
Функция ПроверитьПодключение(ПараметрыПодключения)
```

### 5. Функция-конструктор описывает схему сама

```bsl
// Аннотация не требуется.
//
// Возвращаемое значение:
//  Структура:
//   * АдресСервиса - Строка - адрес конечной точки API.
//   * Таймаут - Число - таймаут подключения в секундах.
//   * ПовторятьПриОшибке - Булево - признак повторного запроса.
//   * Заголовки - Соответствие из КлючИЗначение:
//     * Ключ - Строка - имя HTTP-заголовка.
//     * Значение - Строка - значение HTTP-заголовка.
//
Функция ПараметрыПодключенияКAPI()
```

## Практическая эвристика

При массовом рефакторинге сначала допустимо временно восстановить структуру
заголовков, но перед финализацией нужно пройтись еще раз и выбрать одно из двух:

- полезная содержательная аннотация;
- `Аннотация не требуется.`

Третьего варианта в финальном коде быть не должно.
